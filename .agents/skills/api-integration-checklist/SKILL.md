# 接口联调：契约校验、阻断与确认单

联调阶段后端接口常常不完整：接口还没写、字段还没加、文档滞后于实现。本技能是硬规范，三条底线：

1. **禁止私自脑补**：UI/业务所需数据在接口契约中不存在时，严禁自行捏造字段名或写死 Mock 数据。按需求清单先行开发的静态页面、其中的本地占位数据不属于本条禁令——联调替换时以契约字段替换占位，未替换到的占位清理干净。
2. **阻断并生成确认单**：一旦检测到接口缺失、字段缺失、类型不匹配或行为异常，立即暂停业务代码生成，先输出确认单。
3. **实时更新、跑通即删**：《接口联调清单.md》是当前未决缺口的实时快照——新缺口随时进单，已跑通的条目随时删除，不做历史归档。

## 什么是"契约"（证据源优先级）

凭"这类接口一般都会有这个字段"的印象写代码，就是脑补。写进代码的每个接口路径、字段名、类型，必须能对应到以下证据源（按可信度排序）：

1. 项目内的 API 定义：OpenAPI/Swagger 文件、proto 文件、openapi-typescript 等工具生成的 TS 类型
2. 后端代码（monorepo 或同仓库中可见的 controller / handler / 路由定义）
3. 实际响应：可直接调用的接口（curl、测试环境）的真实返回
4. 用户在对话中明确给出的文档、截图或说明

注意：需求描述（如"页面要展示用户昵称"）只说明业务意图，不构成字段存在的证据——字段叫什么、是否存在，永远按上面的可信度排序核对。

所有证据源都找不到前端需要的信息 → 判定为缺失项，走下面的阻断流程，而不是"按惯例补上"。

## 响应壳与业务码：先读项目现有请求层

写接口调用代码前，先读项目已封装的请求层（axios/fetch 实例、拦截器、统一错误处理），确认三件事——响应包装结构（统一壳 `{ code, data, message }` 还是裸数据本体）、成功判定（判业务码 `res.code === 0` / `res.code === 200` / `res.success === true` 还是只看 HTTP 状态码）、错误处理（拦截器是否已统一弹错提示/上报/跳登录、哪些业务码需业务代码单独处理）；不按"行业惯例"默认 `{ code, data, message }`。

证据强度：拦截器源码是既定事实，先读它；再对照实际响应或契约文档验证。两者矛盾——拦截器按 `code === 0` 判成功，实际响应却是裸 data、壳结构不同、或业务码语义不符——说明请求层与真实契约脱节，这本身就是缺口，走阻断流程，禁止在业务代码里写 `res.data || res` 这类多路径兼容。

新接口的调用代码沿用请求层既有模式：拦截器已解壳的直接取 `data`，未解壳的按项目现有取值方式取；禁止为新接口另起一套成功判定。

## 接口字段 ≠ 页面展示字段

契约决定数据有什么，不决定页面展示什么。展示优先级：用户明确需求 → 现有页面设计 → 现有代码实现 → 接口数据，**接口数据不能反向决定 UI**。

1. **接口多返回字段是正常情况**。页面只使用契约字段的一部分是常态，不要为「字段利用率」补齐 UI：接口返回了 `logisticsCompany`，现有表格只有三列就保持三列，禁止擅自加「物流公司」列。
2. **新增展示字段的合法依据只有四种**：用户明确要求、UI/产品设计明确要求、当前任务明确要求、完成当前需求所必需。四种之外，即使契约里有该字段也不展示。
3. **修改已有页面遵循最小变更**。给 C 加点击事件就只加点击逻辑，禁止顺便调整列顺序、修改字段名、增加展示区域、重构布局；修改前先确认现有的列、按钮与交互，除非需求明确要求，现状视为不可变更项。

## 工作流程

### 1. 先定位契约，再写代码

动手前先搜出项目里的 API 定义（`swagger` / `openapi` / `*.proto` / `src/api/` 等）和已封装的请求层（axios 实例、拦截器），按上节确认响应壳结构与成功判定模式。找不到任何契约时，先向用户要接口文档，不要开始猜接口。

### 2. 逐项核对

写请求层和 TS 类型定义时，逐项核对：路径、方法、请求参数、响应壳结构与成功判定（沿用请求层既有模式）、响应字段、枚举值含义。类型从契约对照生成，不凭记忆手写。

### 3. 检测到缺口，立即阻断

出现以下任一情况，停下当前业务代码生成：

- **缺失接口**：功能需要的 endpoint 在文档、后端代码、实际调用中都找不到，或调用返回 404
- **缺失字段**：接口存在，但响应/文档中没有前端需要的字段
- **类型不匹配**：字段存在但类型、结构或语义与契约不符（包括文档未说明枚举值对应关系这类"说不清"的状态）
- **行为异常**：接口存在、字段也在，但行为不对——返回 5xx、参数不生效（分页、筛选被忽略）、数据明显错误

阻断的范围是**踩在缺口上的功能**：不依赖该缺口的其他部分可以继续开发，但交付时必须说明哪些功能被阻断、等待什么确认。

### 4. 输出确认单

写入项目根目录的 `接口联调清单.md`（文件名固定，不要改）：

- 文件不存在 → 按下方模板创建
- 文件已存在 → 每个受影响模块一张确认单（`##` 级标题）：同一模块再次发现缺口就更新那张单，新模块追加新单；同一缺口影响多个模块时不开重复单，在已有确认单的"涉及页面/模块"里并列列出。去重，不覆盖用户手写的内容
- 没有缺失的分类，直接省略对应小节
- 清单是联调期的临时快照，默认不纳入版本管理（不主动提交进 git）；如团队需要随代码留痕，由用户明确要求后再提交
- 同时在回复中呈现确认单要点，让用户可以直接复制转发给后端

### 5. 临时处理方案（二选一，在确认单中勾选）

- **用户明确同意 mock** → 在集中的临时适配文件里占位（如 `mock/temp-adapter.ts`；项目已有 msw、mockjs、vite-plugin-mock 等方案时优先用现有的），占位代码注明对应的确认单条目和替换条件；确认单勾选第一项
- **未获同意或用户要求严格** → 标记阻塞，勾选第二项，待后端/用户确认后继续

### 6. 实时更新：跑通即删除

《接口联调清单.md》记录的是**此刻仍未解决的缺口**，联调全程持续维护：

- 联调/调试会话一开始，先读根目录清单，未决条目就是本次优先核对、优先验证的对象
- 每拿到一次真实响应（curl、页面请求、接口测试），顺手对照清单，按以下依据删除已解决条目（任一成立即可）：之前缺失的接口返回正常且所需字段齐全、行为符合预期；契约文件已更新且包含该接口/字段；用户明确说"跑通了"
- 只凭"后端说改好了"但还无法验证时，条目状态改为"待验证"，保留到实际跑通为止
- 删除条目时同步清理它的临时处理（移除临时适配文件里的占位、把可选链/TODO 换成真实逻辑）；本次能顺手做就做，做不了必须在回复中提醒。权限：清单文件与本流程创建的临时适配文件属任务内产物，可直接增删；正式业务代码中的占位替换属代码修改，需用户确认跑通或明确同意后再动手
- 清单清空后，删除整个《接口联调清单.md》文件，并在回复中说明

### 7. 会话收尾

联调会话结束或阶段性收工时，按本次情况收尾：

- **本次未检测到缺口** → 回复里一句话说明「契约齐全，未触发清单流程」即可，不必逐条作答。
- **检测到缺口，或清单尚有未决条目** → 在回复里逐条回答以下问题，每条都必须给出明确答案，不允许略过：

1. 本次是否检测到接口缺口？
2. 检测到缺口时，是否已写入《接口联调清单.md》并在回复中呈现确认单要点？
3. 是否存在临时 mock / 占位代码？分别位于哪些文件？
4. 清单中还有几张确认单、共几条未决、哪些处于"待验证"？
5. 建议下一步找后端确认什么？

### 加载态（loading）处理

1. **按需添加，不滥用**：只在用户需要等待反馈的界面交互处加 loading（如表单提交、列表首屏加载、关键按钮请求）；非阻塞、用户无感知的后台请求不加。能用局部状态就不用全局 loading。

2. **用 `finally` 兜底关闭，不写 `try/catch`；`catch` 按需加**：请求不论成功或失败，都在 `.finally()` 中关闭 loading，避免异常路径下 loading 残留。`.finally()` 必须挂；`.catch()` 只在必须就地处理错误时才加，不要无脑加——错误通常由 api 层或调用方统一处理。promise chain 与 async/await 都挂 `.finally()` 收尾，不要用 `try/catch` 包裹。

   - 需就地处理错误：`fetchData().catch(handleErr).finally(() => { loading.value = false })`
   - 无需处理错误：`fetchData().finally(() => { loading.value = false })`
   - async/await：`const data = await fetchData().finally(() => { loading.value = false })`
   - 坏：只在 `then` 里关、`catch` 里漏关——报错后 loading 永远卡住；或把 `finally` 包进 `try/catch` 里。
   - 本条只负责 loading 的兜底关闭，不为关 loading 而引入 `try/catch` / 无脑 `catch`。

3. **状态归属与 composable 规则一致**：loading 若被多组件复用（如 `useList: loading + list + fetchList`），在 composable 内部管理，调用处不重复 `finally`；仅单组件使用时留在组件内（见 AGENTS.md 5.7）。

4. **`.finally()` 挂在哪条链上，是行为差异不是风格问题**：请求后面还跟着别的 `await`（如先拉详情、再预加载级联选项）时，`.finally()` 要挂在整条链上，才能保持「全部完成才收尾」的原有语义；只挂在第一个请求上会让 loading 提前消失——这是行为改变，不是化简，必须说明。

5. **去掉 `try` 后不再 `await` 时，函数改返回 promise**：否则调用方拿不到链，无法自己 `.finally()` 收尾。是否保留 `async` 只看还用不用 `await`，不要为了「消灭 async」把线性代码改成嵌套 `.then`。

6. **`.catch()` 里只留就地状态处理，不重复网络提示**：项目请求层（拦截器）通常已统一 toast，业务侧再 `layer.msg(err.message)` 会叠成两条。`catch` 保留的是错误后必须复位 / 清空的派生状态（如清掉按旧输入算出的值），提示交给请求层。

7. **固定形态**：收尾一律走第 2 条的两种形态——`await req().finally(closeLoading)`；需就地处理错误时 `req().catch(handleErr).finally(closeLoading)`，收尾函数命名 `closeLoading`。

## 确认单模板

```markdown
# 接口联调清单

> 当前未决接口缺口的实时清单：新缺口随时记录，跑通即删除；全部解决后本文件会被移除。

## 📋 确认单——[页面/模块名]

- **涉及页面/模块**：[具体页面或功能]
- **涉及接口**：`[POST/GET /api/xxx]`
- **状态**：待后端确认 / 待验证（后端已改，未实测）

### 1. 缺失接口（如有）

| 功能需求 | 建议接口路径 | 请求方式 | 关键入参/出参说明 |
| :--- | :--- | :--- | :--- |
| 例：导出报表 | `/api/report/export` | POST | 需支持按日期范围筛选 |

### 2. 缺失/需确认字段

| 字段名（建议） | 建议类型 | 对应前端展示/逻辑 | 当前文档状态 | 补充建议 / 疑问 |
| :--- | :--- | :--- | :--- | :--- |
| `avatarUrl` | string | 用户头像展示 | 缺失 | 用户信息接口中未返回头像地址 |

### 3. 行为异常

| 接口 | 异常现象 | 预期行为 | 复现说明 |
| :--- | :--- | :--- | :--- |
| `GET /api/orders` | 分页参数不生效，始终返回第一页 | `page` 参数控制页码 | `page=2` 与 `page=1` 返回内容相同 |

### 4. 前端临时处理方案

- [ ] 已在临时适配文件（如 `mock/temp-adapter.ts`）中暂时 Mock 占位
- [ ] 阻塞当前开发，待后端确认后继续
```

## 边界情况

- **文档与实际返回矛盾**：以实际返回为准写代码，同时在字段表"当前文档状态"列注明矛盾点。
- **契约齐全、无缺口**：正常开发，不生成清单，也不要生成空清单。
